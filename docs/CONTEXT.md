# Контекст проекта (для новых чатов с Claude)

Этот файл — сводка по состоянию проекта и важные технические нюансы, накопленные в переписке с Claude. Цель: чтобы новый чат мог продолжить работу без повторного набивания тех же шишек.

## Как устроена работа с Claude в этом проекте

- Backend на Render (`kaspi-dashboard-r8o3.onrender.com` на момент записи), frontend на Vercel, база — Postgres.
- Claude **не имеет доступа к локальной базе данных** (нет `DATABASE_URL` локально) — все backend-изменения проверяются на реальных данных через `curl` к продакшену с токеном сессии (см. ниже), а не локальным запуском.
- Стандартный цикл: Claude пишет код → `node --check` на backend-файлах → `npm run build` на frontend → проверяет, если это возможно (см. следующий пункт) → чистит `node_modules`/`dist` → **сразу коммитит и пушит, не спрашивая подтверждения** (владелец явно попросил об этом 2026-08-18: «всегда комить и пуш сразу»; до этого правилом было спрашивать «Коммитить и пушить?» и ждать «да»). Один коммит = одно осмысленное изменение, не смешивать несвязанные правки.
- **Как проверять фронтенд, когда базы локально нет** (приём, отработанный 2026-08-24, экономит цикл деплоя):
  - *Вёрстку* — собрать `npm run build`, затем положить в `frontend/dist/` статическую HTML-страницу, которая подключает **собранный** `dist/assets/index-*.css` и повторяет разметку нужного куска UI, поднять `python3 -m http.server` и открыть в Browser pane. Так проверяются реальные стили, а не догадки: именно так были замерены «крестик уехал на 336px выше экрана» и ширины колонок в форме поставки. Важно: `npm run build` затирает `dist/`, поэтому HTML-стенд надо пересоздавать после каждой пересборки.
  - *Логику* — вырезать нужные функции/строки **из настоящего исходника** во временный файл и прогнать в Node. Бэкенд-хелперы экспортируются как есть; во фронтенде `import.meta.env` заменяется литералом, и файл запускается как `.mjs`. Так были проверены таймауты `apiRequest` (поднят сервер, который принимает запрос и молчит) и совпадение расчёта себестоимости между фронтом и бэком.
  - Чего так проверить НЕЛЬЗЯ: ничего, что требует БД или логина. Такие вещи — только после пуша, через `curl` к продакшену.
- Деплой на Render занимает от 1 до 10+ минут, иногда отдаёт 502 на первый долгий запрос сразу после деплоя — тогда просто повторить запрос.
- Чтобы Claude мог проверять API после пуша, нужен токен сессии: залогиниться на сайте, в консоли браузера выполнить `localStorage.getItem('auth_token')` и прислать значение.
- Токены сессий (`sessions` в БД, см. `backend/routes/auth.js`) **не имеют TTL** и не протухают сами по себе — только по явному logout этим же токеном или ручной чистке таблицы. Проверить, жив ли токен: `GET /api/auth/me` с заголовком `X-Session-Token` → `200` живой, `401` — протух/невалиден.
- **При живой проверке UI через Browser pane НЕ кликать по сырым пиксельным координатам скриншота** — screenshot-space и реальный viewport могут не совпадать (особенно после resize/reload), и клик может попасть не туда. Один раз так случайно попали по "Выйти" вместо нужного пункта меню — это удалило сессию ИМЕННО ТЕМ admin-токеном, который переиспользуется в crontab на Oracle (см. ниже) для 3-разовой синхронизации, и тихо сломало продакшен-автоматизацию. Всегда кликать через `ref` из `read_page`, не через `computer{coordinate}` с угаданными координатами. Также нативные `confirm()`-диалоги (например, подтверждение удаления) браузерная автоматизация тихо отклоняет — для таких действий при тестировании проще дёрнуть DELETE напрямую через `curl`, чем жать кнопку в UI.

## Инфраструктура: почему Render не засыпает (Oracle-будильник)

Backend на Render — **бесплатный тариф**, сам по себе засыпает после ~15 минут без входящих запросов. Чтобы дашборд не тормозил на первом заходе и данные не протухали, есть внешний "будильник" на отдельной Oracle Cloud VM:

- **Где:** Oracle Cloud (Always Free), аккаунт `esenzhannur`, регион **Japan Central (Osaka)** (`ap-osaka-1`), инстанс называется **`expense-bot`** (тот же сервер использует другой проект пользователя — expense-бот, название не про kaspi-dashboard, но crontab общий на оба).
- **Доступ:** SSH, пользователь `ubuntu`, публичный IP на момент записи `217.142.234.123`. Приватный ключ лежит локально у владельца: `~/Downloads/ssh-key-2026-07-06.key` (+ `.pub`), дата в имени совпадает с датой создания инстанса (Jul 06, 2026).
- **Что в `crontab -l` на этой VM:**
  - `*/10 * * * * curl -s https://kaspi-dashboard-r8o3.onrender.com/health` — пинг каждые 10 минут, держит Render постоянно разбуженным (интервал меньше 15-минутного тайм-аута сна).
  - `0 8,14,20 * * * curl -X POST .../api/sync -H "X-Session-Token: <токен>" -d '{"days":1}'` — полноценная синхронизация заказов 3 раза в день (08:00 / 14:00 / 20:00 UTC = 13:00 / 19:00 / 01:00 по времени Казахстана), с зашитым токеном сессии админа.
- **Риски:** единая точка отказа — если Oracle когда-нибудь заберёт этот Always Free ресурс, или инстанс остановят/удалят, будильник и 3-разовая синхронизация пропадут молча, без уведомления. Также если токен в crontab когда-нибудь протухнет (см. выше про TTL — маловероятно, но возможно при ручном logout/сбросе БД) — синхронизация 3 раза в день перестанет работать, а `/health`-пинг продолжит держать сервис живым, что может маскировать проблему.
- Если нужно поменять токен в crontab — зайти по SSH и `crontab -e`.

## PWA и офлайн-режим (`frontend/public/sw.js`)

- Приложение — SPA без роутера (одна `/`, переключение "страниц" — просто состояние в React, не URL), поэтому офлайн-кэшу достаточно ловить `/` + бандл + API-запросы, отдельные маршруты не нужны.
- **Кэш используется ТОЛЬКО для офлайна.** Обе группы запросов (`kaspi-static-v3` — свой домен, HTML/JS/CSS/иконки; `kaspi-api-v3` — backend на Render) работают по "network first, cache fallback": пока есть сеть, всегда идёт живой запрос на сервер и пользователь видит только реально свежие данные (с обычным индикатором загрузки), кэш просто наполняется по пути. Кэш достаётся, только если сеть недоступна. Кэшируются только GET-запросы; мутации (POST/PUT/DELETE) сознательно не трогаются и не подменяются — офлайн они должны честно падать с ошибкой.
- **ВАЖНО, история решений (весь 2026-08-18, четыре захода — чтобы не ходить по кругу заново):**
  1. `sw.js` изначально был no-op намеренно: "дашборд должен всегда показывать только свежие данные". Пользователь попросил офлайн-доступ → сделали network-first с офлайн-фолбэком.
  2. Попросила "и онлайн показывать кэш сразу, а свежее грузить в фоне" → API перевели на stale-while-revalidate.
  3. Из-за (2) экран мгновенно показывал старые цифры без признака устарелости. Пробовали помечать такие данные притемнением: сначала по флагу `loading` (не сработало — кэш резолвится за миллисекунды, `loading` не успевает быть видимым), потом по реальному возрасту данных из HTTP-заголовка `Date` с порогом 60 минут (`useDataFreshness.js` + `getFetchedAt` в `api.js`). Пользователь сообщил, что всё равно не работает.
  4. **Итог: от stale-while-revalidate и от индикации устарелости отказались полностью** — вернулись к простой и предсказуемой схеме "онлайн = только свежее, офлайн = кэш" (текущее состояние). `useDataFreshness.js` и `fetchTimestamps`/`getFetchedAt` в `api.js` удалены. Если снова захочется "быстро из кэша онлайн" — учитывать, что главная проблема не в скорости, а в том, что пользователю невозможно понять, свежие цифры на экране или нет.
- **Обновление данных при переходе на раздел (осталось от захода 2, полезно само по себе):**
  - `Dashboard.jsx` передаёт каждой странице проп `active={key === safeView}` (и общий `isOnline` из `useOnlineStatus.js`, обёртки над `navigator.onLine` + событиями `online`/`offline`). Страницы НЕ размонтируются при переключении разделов (см. комментарий там про `visited`/`display:none`), поэтому именно `active` — единственный сигнал "пользователь только что открыл этот раздел".
  - Паттерн на каждой странице: `useEffect(() => { if (active) loadX(); }, [active, ...остальные зависимости])` — грузим данные заново при каждом переходе на раздел, не только при первом монтировании.
  - Есть состояние `hasData` (взводится в `.finally()` первой загрузки) — отдельно от `loading`, чтобы отличать "первая загрузка вообще, показывать нечего" (полноэкранный "Загрузка...") от "уже есть что показать, просто перезагружаем".
  - Затемнение (`opacity: 0.55`, тот же приём, что у "Обновить сейчас" на Главной) включается по условию `(loading && hasData) || !isOnline` — во время перезагрузки и постоянно, пока нет сети (офлайн данные гарантированно из кэша).
  - Подключено на всех страницах с данными, кроме `Analyst.jsx` (история AI-отчётов, не "дрейфующие" данные — не подключали).
- Так как кэш ключуется по URL без учёта заголовков, `X-Session-Token` в кэш-ключ не попадает — при смене пользователя в одном браузере какое-то время может отдаваться закэшированный ответ, полученный под другим токеном. Для одного магазина с несколькими доверенными сотрудниками это приемлемо, но если появится по-настоящему разный доступ к данным по пользователям — это стоит пересмотреть.
- **Исключение из "кэшируем только GET":** картинки товаров (`POST /api/product-images`, см. `Warehouse.jsx`/`Purchasing.jsx`) на самом деле чтение, а не мутация — POST используется только потому, что список `product_id` может быть длинным и не влезает в query-строку GET. Картинки хранятся как `data:` URL прямо в JSON-ответе (см. `backend/routes/images.js` — файлового хранилища в проекте нет), поэтому закэшировать сам ответ достаточно, отдельно кэшировать байты картинок не нужно. Кэш-ключ для этого запроса — не URL (он один и тот же для любого списка id), а синтетический `Request` с отсортированными id в query-строке (`cacheKeyForProductImages` в `sw.js`) — иначе "Склад" и "Закуп" с разными наборами товаров подменяли бы друг другу картинки из кэша. Загрузка/удаление картинки (`/api/product-images/upload`, `DELETE /api/product-images/:id`) — это уже настоящие мутации, под это исключение не попадают и кэшу не подменяются.
- Т.к. `index.html` не хешируется по содержимому (в отличие от `dist/assets/*.js`/`*.css` от Vite), после деплоя новой версии фронтенда браузер подхватывает новый `sw.js` автоматически при следующем визите (`skipWaiting()` + `clients.claim()` в `activate`), без ручной чистки кэша пользователем.

## Основные фичи и где они живут

### Отчёт / Главная — расчёт чистой прибыли
- `backend/routes/stats.js` — `computeSummaryNetProfit()` считает чистую прибыль на "Главной" за период по ВСЕМ товарам, с **прогнозом** для заказов без загруженного Excel-отчёта Kaspi Pay (берёт средний % прибыли по тому же товару за период, с запасными вариантами: все товары за период → окно 60 дней назад → 0).
- Маркетинг (реклама + бонусы от продавца + бонусы за отзыв) вычитается из чистой прибыли на Главной без прогноза — просто сумма того, что реально загружено (`fetchMarketingTotalForRange`).
- `backend/routes/stats.js` — `/api/stats/product/:productId` (для графика в `ProductDetail.jsx`) теперь тоже прогнозирует чистую прибыль для дней без Excel-отчёта (раньше был разрыв `null`) — использует исторический % прибыли ЭТОГО товара за всю историю. Фронтенд рисует прогнозную часть графика пунктиром (`SalesChart.jsx`, проп `estimatable`).
- ROI везде считается как `Чистая прибыль / (Себестоимость + Маркетинг + Услуги ФФ/Упаковка + Прочие расходы)` — комиссия, доставка и налоги в знаменатель НЕ входят.

### Проверка доставки (Заказы)
- `backend/routes/reports.js` — `GET /api/reports/delivery-anomalies` — сравнивает доставку по заказам с ОДНИМ товаром с медианной доставкой для этого же товара, помечает отклонения от 1.5x и минимум 200 тг разницы. Кнопка на странице "Заказы" (`frontend/src/Orders.jsx`).
- ВАЖНО: `percentile_cont` в Postgres — это ordered-set aggregate, его **нельзя** использовать с `OVER` (window). Медиану считаем в JS.

### Проблемные возвраты (новая страница, только admin)
Отслеживает заказы, отменённые при доставке Kaspi, и проверяет, не потерял ли их Kaspi/партнёр по фулфилменту.

**Файлы:**
- `backend/kaspiClient.js` — `fetchOrdersByStatus(state, status, dateFromMs, dateToMs, chunkDays)` — ищет заказы Kaspi по state/status за диапазон дат (у Kaspi жёсткий лимит **14 дней** на диапазон creationDate за один запрос — чанкуем). `fetchOrderByCode(code)` — live-статус одного заказа (внутренний id Kaspi = `base64(order_code)`, лукап не нужен).
- `backend/kaspiLogistics.js` — публичный (без токена!) трекинг `https://logistics.kaspi.kz/core/api/public/support?orderId=<код>`.
- `backend/wonderClient.js` — интеграция с партнёром Wonder (принимает физически возвраты/отмены), логин по email/паролю (`WONDER_EMAIL`, `WONDER_PASSWORD` на Render), эндпоинт `https://api.d.wonder-fulfillment.kz/api/refund-order-groups/seller/?page=X&size=Y&status=STATUS` (статусы: `REQUEST`, `WAITING`, `ACTIVE`, `ARCHIVE`).
- `backend/deliveryReturnsSync.js` — вся логика синхронизации (см. ниже).
- `backend/routes/deliveryReturns.js` — `GET /` (список + вычисление "подозрительности"), `POST /sync` (ручной/ночной запуск всех проверок), `DELETE /:orderNumber` (пользователь убирает строку вручную).
- `frontend/src/DeliveryReturns.jsx` — таблица с фильтрами (как на "Заказы"), плюс отдельная таблица снизу для заказов, отменённых ДО передачи в доставку.
- Таблица в БД: `delivery_cancellations` (см. `backend/db.js`).
- Ночной cron в `server.js` (в 03:00): `syncDeliveryCancellations` (последние 2 дня) → `refreshTrackedOrders` → `refreshTrackingStatuses` → `refreshWonderReceived`.

**КРИТИЧЕСКИ ВАЖНЫЕ находки об API Kaspi (наступили на грабли трижды подряд — не повторять!):**
1. `kaspiDelivery.returnedToWarehouse` (в основном Orders API) — **ненадёжное поле**. У реально вернувшегося заказа было `false`. Не использовать как признак "потерян".
2. Верхнеуровневые поля ответа трекинга (`orderStatus`, `active`, `lastActualTrack`) на `logistics.kaspi.kz` — тоже **могут противоречить** собственному массиву `tracks` в том же ответе (пример: `active: true`, `lastActualTrack: null`, но в `tracks` есть `RETURNED` с датой). **Единственный надёжный источник — сам массив `tracks`**: ищем код `RETURNED` (значит точно вернулся), и берём дату САМОГО ПОЗДНЕГО события оттуда.
3. "Активно возвращается" (`tracking_active = true`, применяется порог дней) — определяется ТОЛЬКО если последнее по времени событие в `tracks` начинается с `RETURN_`. Любой другой последний код (`CANCELLED`, `WAITING_IN_PICKUP_POINT`, `WAYBILL_CREATED` и т.п.) — считается разрешённым, не подозрительным, даже если это выглядит как "нет движения давно" — эти заказы просто не проходили полный цикл возврата (например, отменили ещё до отправки).
4. Заказы с последним кодом `CANCELLED` (без единого шага доставки в `tracks`) = отменены ДО передачи в доставку — показываются в ОТДЕЛЬНОЙ таблице снизу, никогда не подозрительны.
5. Порог "подозрительности" (застрял в реальном возврате) = **45 дней** без движения — согласовано с владельцем магазина.

**Про Wonder:** пересечение с нашим списком реальных возвратов (тех, что уехали в доставку) показало, что **~179 из 214** отсутствуют у Wonder вообще — включая заказы с подтверждённым по трекингу Kaspi статусом "RETURNED". Причина не выяснена до конца: либо не все возвраты физически идут через Wonder, либо Wonder теряет часть регистраций. Колонка "Принят складом" (Да/Нет) в таблице просто показывает факт присутствия номера заказа в списке Wonder (`REQUEST`+`WAITING`+`ACTIVE`+`ARCHIVE`), без доп. интерпретации.

### Склад / Поставки / Закуп (снабжение)
- И "Склад", и "Поставки" рендерят отдельную таблицу на каждый город (Алматы/Астана/...), а не одну общую со столбцом "Склад" — паттерн: сгруппировать по `warehouse`, отсортировать города через `localeCompare(..., 'ru')`, на каждую группу свой `<div className="section-title">{city}</div>` + `<div className="card">`.
- **Склады описаны в ОДНОМ месте — `backend/warehouseMapping.js`.** Там массив `WAREHOUSES`: код точки продаж Kaspi (`pickupPointId`), город, роль (`main` — идёт в «Основной отчёт» и на Главную, `selfbuy` — считается отдельно) и `display` (показывать ли на «Складе»). Все прочие списки (`ALL_CITIES`, `MAIN_CITIES`, `SELF_BUY_CITIES`, `DISPLAY_CITIES`, `CITY_ORDER`, `PICKUP_POINT_WAREHOUSE_MAP`) выводятся из него автоматически. **Чтобы добавить склад — допиши одну строку**, больше ничего править не нужно; фронтенд получает список складов с сервера в ответе `GET /api/batches`, своей копии не держит. До 2026-08-29 эти сведения были размазаны по восьми спискам в шести файлах и успели разъехаться: «основной магазин» на Главной означал «всё, кроме самовыкупов» (то есть включал заказы без склада), а в «Отчёте» — «ровно Алматы и Астана». Теперь оба экрана спрашивают `MAIN_CITIES` у справочника.
- **Заказ с неизвестной точкой продаж больше не пропадает молча.** Если Kaspi заведёт новую точку, её кода не будет в справочнике, `origin_city` станет `NULL`, и заказ выпадет из «Отчёта», со «Склада» и из расчёта себестоимости. `GET /api/orders` возвращает `unknownPickupPoints` (код точки, число заказов, диапазон дат), а страница «Заказы» показывает по ним предупреждение — видно, какую строку дописать в справочник. Миграция в `db.js` при каждом старте пересчитывает `orders.origin_city` из сохранённого `pickup_point_id`, поэтому добавление склада чинит и уже загруженные заказы задним числом.
- `product_batches.status` — `'received'` (по умолчанию, физически на складе) или `'in_transit'` (заказано у поставщика, ещё в пути). `computeWarehouseStock()` в `backend/routes/warehouse.js` считает FIFO-остаток **только** по `status='received'` — in_transit-партии в реальный остаток склада не входят. Кнопка "Отметить прибывшим" (`POST /api/batches/:id/receive`) переводит статус в received и проставляет `received_date = сегодня`.
- **Фильтр `status = 'received'` обязателен ВЕЗДЕ, где считается FIFO — а копий формулы три.** Кроме `computeWarehouseStock()` это `computeCosts()` в `backend/costEngine.js` (себестоимость по заказам и месяцам) и в `backend/routes/stats.js` — `computeCostsByOrderItem()` (разбивка по товарам в "Отчёте") и `computeProductDailyCost()` (дневной график товара). До 2026-08-28 фильтра не было ни в одной из этих трёх: FIFO, исчерпав прибывшие партии, молча переходил на партию "в пути" и брал её цену. Заказ 1047398639 (Проектор TOMMILI LUMIX HD, выручка 69 900 ₸) оказался 114-й проданной единицей при 113 прибывших и получил себестоимость 1 464 000 ₸ с ещё не приехавшей партии — маржа −2009%. Симптом узнаваемый: **одна и та же партия одновременно "не в остатке" на Складе и "продана" в Отчёте**. Если будешь добавлять четвёртое место с FIFO — фильтр не забудь.
- **Oversold (продано больше, чем приехало) оценивается по цене ПОСЛЕДНЕЙ прибывшей партии.** Раньше такая часть продажи оставалась вообще без себестоимости, и заказ показывал прибыль, равную всей выручке — это хуже любой оценки. Оценка самоисправляющаяся: FIFO считается с нуля при каждом вызове, поэтому как только партия отмечена прибывшей (`received_date = сегодня`, то есть она встаёт в конец очереди FIFO), те же продажи пересчитываются по её настоящей цене. Реализовано во всех трёх копиях FIFO. **Если прибывших партий нет вообще** (весь товар ещё в пути) — себестоимость остаётся неизвестной; цену партии "в пути" не берём даже как оценку, именно это было багом заказа 1047398639.
- На "Поставках" столбец "Остаток" (`remaining_quantity`) убран из таблицы — это поле не уменьшается продажами (см. предупреждение в `warehouse.js` выше), почти всегда совпадает с "Заявлено" и вводило в заблуждение. Настоящий остаток — только на "Складе".
- Даты на "Поставках" — через `formatDateDMY()` из `dateUtils.js` (DD/MM/YYYY); при редактировании поставки `received_date` из базы (полный ISO-таймстамп) нужно резать до `slice(0,10)` перед тем, как класть в `<input type="date">`, иначе поле останется пустым.
- **Калькулятор валюты в форме поставки** — `purchase_price`/`logistics_cost` в базе всегда в ₸ за 1 шт (это единственное, что участвует в расчёте себестоимости и `cost_price`). Поставщикам обычно платят в $ или ¥, логистику — то в ₸, то в $, поэтому в форме есть два блока-калькулятора выше итоговых полей: "Сумма закупки за партию" + валюта (₸/$/¥) + "Курс", и "Логистика за партию" + валюта (₸/$) + "Курс" — каждый умножает сумму на курс, делит на количество и подставляет результат в поля "...за 1 шт, ₸". **Эти итоговые поля — не `input`, а нередактируемые значения** (`.batch-computed-value`): их просили сделать «только для информации», чтобы посчитанное нельзя было случайно разойтись с введённым. Из-за этого у формы нет HTML-валидации `required` на цене, поэтому в `handleSubmit` стоит ручная проверка «цена за 1 шт ещё не рассчиталась». Когда выбрана валюта ₸, поле "Курс" отключается (курс = 1). Сумма/валюта/курс дополнительно сохраняются в БД (`purchase_currency`, `purchase_amount_foreign`, `purchase_rate`, `logistics_currency`, `logistics_amount_foreign`, `logistics_rate` — все nullable) чисто как справочная информация для истории, в формулах себестоимости не участвуют. У партий, добавленных до этой фичи (или где калькулятор не использовался), эти поля `NULL`.
- **Форма поставки разбита на смысловые блоки** (`.form-section` + `.form-section-title` + `.form-section-hint` в `Batches.jsx`/`styles.css`), порядок фиксированный и осмысленный: **Товар → Партия → Закупка → Логистика → Прочие расходы → Себестоимость за 1 шт → Примечание**. Полей в форме ~14, без блоков на телефоне это сплошная лента. Разделители — тонкие линии (`border-top`), а не вложенные рамки: модалка и так на `--bg-card`, поля на `--bg`, третий уровень вложенности выглядел бы тяжело. Исключение — итоговый блок `.form-section-result`, он специально выделен фоном как результат.
  - **"Количество" стоит в блоке "Партия", то есть ВЫШЕ блоков с суммами** — это не косметика: обе суммы (и прочие расходы) делятся именно на количество, и спрашивать его последним было логически неправильно.
  - Итоговая строка (`.batch-result-row`) — `auto-fit`-сетка, потому что значений то 3, то 4: колонка "Прочие" появляется только когда прочие расходы реально заполнены.
- **Прочие расходы на партию (сертификаты, НДС, растаможка, ...)** — произвольный список строк `{ name, amount, currency, rate }`, названия придумывает пользователь. Хранятся в `product_batches.extra_expenses` (JSONB, nullable) — не отдельными колонками и не отдельной таблицей, потому что длина списка заранее неизвестна, а выбирают их всегда вместе с самой партией, join не нужен. Суммы указываются за ВСЮ партию (как закупка и логистика), а в `cost_price` попадают уже поделёнными на количество.
  - **Это влияет на деньги во всём приложении:** `cost_price` = закупка/шт + логистика/шт + прочие/шт, а `cost_price` — единственный источник себестоимости для FIFO-списания (`costEngine.js`), оценки склада (`warehouse.js`) и расчёта прибыли (`stats.js`). То есть прочие расходы автоматически уменьшают показываемую прибыль. Пересчёт происходит только при сохранении партии — у поставок, созданных до появления этой фичи, `extra_expenses` = `NULL` и `cost_price` не меняется.
  - Валидация — `normalizeExtraExpenses()` в `backend/routes/batches.js`: строки без названия или без суммы молча отбрасываются (это необязательная часть формы, одна пустая строка не должна ронять сохранение всей поставки), название режется до 60 символов, список — до 20 строк, для `KZT` курс всегда принудительно 1, для остальных валют забытый курс превращается в 1 (а не в 0, иначе расход бесследно исчез бы из себестоимости).
  - **Условия отбора строк продублированы на фронтенде** (`filledExpenses` в `Batches.jsx`) — специально совпадают с бэкендом, иначе предпросмотр "Себестоимость за 1 шт" в форме разошёлся бы с тем, что реально сохранится. Если менять правила отбора — менять в обоих местах.

### Закуп (планирование пополнения) — `backend/routes/purchasing.js`, `frontend/src/Purchasing.jsx`
Страница под "Складом" (только admin), список товаров с рекомендацией "сколько и когда закупать". Считается по классической модели **(s, S)**:
- `s` (точка заказа) = Прод./день × `lead_time_days` × (1 + `buffer_pct`/100) — порог для статуса Критично/Скоро.
- `S` (уровень пополнения) = `s` + Прод./день × `lead_time_days` — цель, до которой считается "К закупу" (`Math.ceil(S − остаток)`), **независимо от того, ниже ли остаток точки s** — поэтому "К закупу" может быть > 0 даже когда остаток уже выше точки заказа. Это НЕ проверено против реального стороннего инструмента с того скриншота, откуда бралась идея страницы — формула подобрана так, чтобы сошлись 3 примера чисел с скриншота, но это реконструкция, а не подтверждённый факт. Если пользователь скажет, что цифры "не такие", это первое, что нужно перепроверить.
- Статус: Критично — дней остатка < `lead_time_days`; Скоро — < `lead_time_days × 1.5` (тоже собственное предположение, порог с скриншота не восстанавливался); иначе В норме.
- Прод./день = среднее за последние 30 дней (`order_items` за `VALID_STATUSES`, см. `warehouse.js`).
- `lead_time_days`/`buffer_pct` — настраиваются в UI ("Настройка параметров"), хранятся в отдельной синглтон-таблице `purchasing_settings` (id=1, дефолт 14 дней / 30%).
- "Доступно" на этой странице — разбивка по ВСЕМ 4 складам (в отличие от "Склада", который сознательно показывает только Алматы/Астана).
- "Экспорт Excel" на самом деле CSV (не добавляли новую зависимость типа `xlsx` в frontend) — открывается в Excel нормально, просто не .xlsx.

## Сетевые запросы фронтенда (`frontend/src/api.js`)

- **У каждого запроса есть таймаут (`AbortController`), и это обязательно.** Было расследование (2026-08-24): пользователь нажал "Сохранить" в форме поставки, кнопка навсегда залипла на "Сохраняем...", помогла только полная перезагрузка приложения. Причина: `fetch` без таймаута на подвисшем мобильном соединении (сеть переключилась, сокет открыт, ответа нет, ошибки тоже нет) **никогда не резолвится и не реджектится** — значит `.finally(() => setSaving(false))` не выполняется ВООБЩЕ, и форма остаётся заблокированной навсегда. Теперь: `DEFAULT_TIMEOUT_MS = 45 с` (с запасом на просыпание Render после простоя), `LONG_TIMEOUT_MS = 5 мин` для тяжёлых операций — `/api/sync`, `/api/expenses/sync`, `/api/delivery-returns/sync`, загрузка Excel и картинок, генерация AI-отчёта, `/api/reports/delivery-anomalies`. Если добавляется новый долгий эндпоинт — не забыть передать ему `{ timeoutMs: LONG_TIMEOUT_MS }`, иначе он будет обрываться на 45-й секунде.
- Таймер снимается в `finally` только ПОСЛЕ чтения тела ответа — зависнуть можно не только в ожидании заголовков, но и на середине чтения.
- Сетевые сбои `fetch` кидает как `TypeError` с техническим текстом ("Load failed"/"fetch failed") — он перехватывается и заменяется на понятную фразу. `UNAUTHORIZED` пробрасывается как есть: на него завязан автоматический выход из аккаунта в `App.jsx`.
- `login()` ходит мимо `apiRequest` (токена ещё нет), поэтому таймаут ему прописан отдельно — иначе точно так же залипал бы экран входа.

## Модальные окна на телефоне
- **Прокрутка страницы под открытым окном заблокирована** (`frontend/src/useBodyScrollLock.js`, подключён в обеих модалках — `Batches.jsx` и `SettingsModal` в `Purchasing.jsx`). Симптом был: тянешь форму, а вместо неё уезжает список поставок на фоне. Две разные причины, лечатся вместе:
  - *scroll chaining* — прокрутка внутри `.modal-box`, дойдя до края, продолжается на фоне. Лечится `overscroll-behavior: contain` (стоит и на `.modal-box`, и на `.modal-overlay`).
  - *сама страница остаётся прокручиваемой* — лечится блокировкой `body`. Именно `position: fixed`, а не `overflow: hidden`: в iOS Safari (а приложение стоит как PWA) `overflow: hidden` на body не удерживает прокрутку. Побочный эффект `position: fixed` — страница прыгает в начало, поэтому хук запоминает `window.scrollY` перед блокировкой, ставит `top: -scrollY`, а при закрытии возвращает позицию через `scrollTo({ behavior: 'instant' })`.
  - **Важно:** хук блокирует прокрутку на всё время жизни компонента, поэтому модалки обязаны монтироваться условно (`{showModal && <BatchModal/>}`), а не прятаться через CSS — иначе прокрутка останется заблокированной навсегда.


- **Шапка модалки (`.modal-header`) — `position: sticky`, а крестик — минимум 44×44 px.** Из того же расследования: пользователь жаловался, что "крестик не работал". Проверено в браузере на ширине 375 px: форма поставки длинная (14 полей), пользователь прокручивает её вниз к кнопке "Сохранить" — и в этот момент крестик оказывался на **336 px выше видимой области**, то есть его физически не было на экране, закрыть окно было нечем. Плюс сам он был 24×27 px при рекомендованном минимуме 44×44. Если будешь трогать `padding` у `.modal-box` — синхронно поправь отрицательные margin/top у `.modal-header` (значения должны совпадать с padding, есть отдельный набор для `max-width: 640px`, где padding 18 px вместо 24 px).

## Известные ограничения / что не доделано
- Токен Wonder (сессионный) живёт ~10 часов — поэтому сделан логин по email/паролю на каждый вызов, а не хранение статичного токена.
- Причина расхождения 179/214 по Wonder не выяснена — возможно, стоит уточнить у самого Wonder или у владельца магазина, весь ли объём возвратов должен идти через этого партнёра.
- Себестоимость возвратов (`STOCK_CUTOFF_DATE` в `constants.js`) — партии считаются снимком на эту дату, заказы старше неё оцениваются по цене первой поставки.
- На "Закупе" сознательно не сделано: карточка "План закупа" (была пустая 0/0 на скриншоте-примере, непонятна без ручного выбора товаров) и предзаполнение формы поставки количеством из "К закупу" — кнопка "Создать поставку" просто открывает "Поставки" пустой формой (так решил пользователь).
