# Контекст проекта (для новых чатов с Claude)

Этот файл — сводка по состоянию проекта и важные технические нюансы, накопленные в переписке с Claude. Цель: чтобы новый чат мог продолжить работу без повторного набивания тех же шишек.

Обновляй этот файл по мере важных изменений — проси Claude дописывать сюда новые находки.

## Как устроена работа с Claude в этом проекте

- Backend на Render (`kaspi-dashboard-r8o3.onrender.com` на момент записи), frontend на Vercel, база — Postgres.
- Claude **не имеет доступа к локальной базе данных** (нет `DATABASE_URL` локально) — все backend-изменения проверяются на реальных данных через `curl` к продакшену с токеном сессии (см. ниже), а не локальным запуском.
- Стандартный цикл: Claude пишет код → `node --check` на backend-файлах → `npm run build` на frontend → проверяет, если это возможно (см. следующий пункт) → чистит `node_modules`/`dist` → **сразу коммитит и пушит, не спрашивая подтверждения** (владелец явно попросил об этом 2026-08-18: «всегда комить и пуш сразу»; до этого правилом было спрашивать «Коммитить и пушить?» и ждать «да»). Один коммит = одно осмысленное изменение, не смешивать несвязанные правки.
- **Как проверять фронтенд, когда базы локально нет** (приём, отработанный 2026-08-24, экономит цикл деплоя):
  - *Вёрстку* — собрать `npm run build`, затем положить в `frontend/dist/` статическую HTML-страницу, которая подключает **собранный** `dist/assets/index-*.css` и повторяет разметку нужного куска UI, поднять `python3 -m http.server` и открыть в Browser pane. Так проверяются реальные стили, а не догадки: именно так были замерены «крестик уехал на 336px выше экрана» и ширины колонок в форме поставки. Важно: `npm run build` затирает `dist/`, поэтому HTML-стенд надо пересоздавать после каждой пересборки.
  - *Логику* — вырезать нужные функции/строки **из настоящего исходника** во временный файл и прогнать в Node. Бэкенд-хелперы экспортируются как есть; во фронтенде `import.meta.env` заменяется литералом, и файл запускается как `.mjs`. Так были проверены таймауты `apiRequest` (поднят сервер, который принимает запрос и молчит) и совпадение расчёта себестоимости между фронтом и бэком.
  - *Целую страницу на ЖИВЫХ данных* (приём 2026-08-29, сильно лучше двух предыдущих): создать
    `frontend/harness.html` + `frontend/src/__harness.jsx`, который рендерит настоящий компонент
    страницы, и `frontend/.env.local` с `VITE_API_URL=https://kaspi-dashboard-r8o3.onrender.com`.
    Токен кладётся в `localStorage` через консоль браузера (в файл писать нельзя — утечёт в git),
    компонент получает его пропсом. Дальше `npm run dev` через Browser pane — и страница работает
    на настоящем продакшен-API со всеми реальными цифрами, до пуша фронтенда. `.env.local` и оба
    файла стенда — в `.gitignore` (один раз стенд уже уехал в коммит).
  - **ОСТОРОЖНО: стенд ходит в ПРОДАКШЕН.** Читать можно свободно, а вот любые сохранения пишутся
    в живую базу. 2026-08-29 тестовое сохранение расчёта юнит-экономики легло на реальный товар,
    владелец через полчаса открыл страницу, эти значения подтянулись в её расчёт и уехали в её
    сохранение. Правило: для проверки мутаций брать заведомо ненужный объект и удалять запись
    сразу после проверки, а лучше — проверять запись через `curl`, а не через UI стенда.
  - Чего так проверить НЕЛЬЗЯ: ничего, что требует БД или логина ЛОКАЛЬНО. Такие вещи — либо
    стендом на продовый API, либо после пуша через `curl` к продакшену.
- Деплой на Render занимает от 1 до 10+ минут, иногда отдаёт 502 на первый долгий запрос сразу после деплоя — тогда просто повторить запрос.
- Чтобы Claude мог проверять API после пуша, нужен токен сессии: залогиниться на сайте, в консоли браузера выполнить `localStorage.getItem('auth_token')` и прислать значение.
- Токены сессий (`sessions` в БД, см. `backend/routes/auth.js`) **не имеют TTL** и не протухают сами по себе — только по явному logout этим же токеном или ручной чистке таблицы. Проверить, жив ли токен: `GET /api/auth/me` с заголовком `X-Session-Token` → `200` живой, `401` — протух/невалиден.
- **Владелец работает в дашборде параллельно с Claude.** Прод — живой: пока идёт задача, там
  может появиться новая запись, сделанная руками. Отсюда два следствия: (1) переименование поля
  формы требует миграции старых сохранений, иначе введённые данные молча пропадают (см.
  `migrateForm` в юнит-экономике); (2) перед выводом «данных нет» стоит перечитать прод, а не
  доверять снимку получасовой давности.
- **При живой проверке UI через Browser pane НЕ кликать по сырым пиксельным координатам скриншота** — screenshot-space и реальный viewport могут не совпадать (особенно после resize/reload), и клик может попасть не туда. Один раз так случайно попали по "Выйти" вместо нужного пункта меню — это удалило сессию ИМЕННО ТЕМ admin-токеном, который переиспользуется в crontab на Oracle (см. ниже) для 3-разовой синхронизации, и тихо сломало продакшен-автоматизацию. Всегда кликать через `ref` из `read_page`, не через `computer{coordinate}` с угаданными координатами. Также нативные `confirm()`-диалоги (например, подтверждение удаления) браузерная автоматизация тихо отклоняет — для таких действий при тестировании проще дёрнуть DELETE напрямую через `curl`, чем жать кнопку в UI.

## Инфраструктура: почему Render не засыпает (Oracle-будильник)

Backend на Render — **бесплатный тариф**, сам по себе засыпает после ~15 минут без входящих запросов. Чтобы дашборд не тормозил на первом заходе и данные не протухали, есть внешний "будильник" на отдельной Oracle Cloud VM:

- **Где:** Oracle Cloud (Always Free), аккаунт `esenzhannur`, регион **Japan Central (Osaka)** (`ap-osaka-1`), инстанс называется **`expense-bot`** (тот же сервер использует другой проект пользователя — expense-бот, название не про kaspi-dashboard, но crontab общий на оба).
- **Доступ:** SSH, пользователь `ubuntu`, публичный IP на момент записи `217.142.234.123`. Приватный ключ лежит локально у владельца: `~/Downloads/ssh-key-2026-07-06.key` (+ `.pub`), дата в имени совпадает с датой создания инстанса (Jul 06, 2026).
- **Что в `crontab -l` на этой VM:**
  - `*/10 * * * * curl -s https://kaspi-dashboard-r8o3.onrender.com/health` — пинг каждые 10 минут, держит Render постоянно разбуженным (интервал меньше 15-минутного тайм-аута сна).
  - `0 8,14,20 * * * curl -X POST .../api/sync -H "X-Session-Token: <токен>" -d '{"days":1}'` — полноценная синхронизация заказов 3 раза в день (08:00 / 14:00 / 20:00 UTC = 13:00 / 19:00 / 01:00 по времени Казахстана), с зашитым токеном сессии админа.
- **Риски:** единая точка отказа — если Oracle когда-нибудь заберёт этот Always Free ресурс, или инстанс остановят/удалят, будильник и 3-разовая синхронизация пропадут молча, без уведомления. Также если токен в crontab когда-нибудь протухнет (см. выше про TTL — маловероятно, но возможно при ручном logout/сбросе БД) — синхронизация 3 раза в день перестанет работать, а `/health`-пинг продолжит держать сервис живым, что может маскировать проблему.
- Если нужно поменять токен в crontab — зайти по SSH и `crontab -e`.

## PWA и офлайн-режим (`frontend/public/sw.js`)

- Приложение — SPA без роутера (одна `/`, переключение "страниц" — просто состояние в React, не URL), поэтому офлайн-кэшу достаточно ловить `/` + бандл + API-запросы, отдельные маршруты не нужны.
- **Кэш используется ТОЛЬКО для офлайна.** Обе группы запросов (`kaspi-static-v3` — свой домен, HTML/JS/CSS/иконки; `kaspi-api-v3` — backend на Render) работают по "network first, cache fallback": пока есть сеть, всегда идёт живой запрос на сервер и пользователь видит только реально свежие данные (с обычным индикатором загрузки), кэш просто наполняется по пути. Кэш достаётся, только если сеть недоступна. Кэшируются только GET-запросы; мутации (POST/PUT/DELETE) сознательно не трогаются и не подменяются — офлайн они должны честно падать с ошибкой.
- **ВАЖНО, история решений (весь 2026-08-18, четыре захода — чтобы не ходить по кругу заново):**
  1. `sw.js` изначально был no-op намеренно: "дашборд должен всегда показывать только свежие данные". Пользователь попросил офлайн-доступ → сделали network-first с офлайн-фолбэком.
  2. Попросила "и онлайн показывать кэш сразу, а свежее грузить в фоне" → API перевели на stale-while-revalidate.
  3. Из-за (2) экран мгновенно показывал старые цифры без признака устарелости. Пробовали помечать такие данные притемнением: сначала по флагу `loading` (не сработало — кэш резолвится за миллисекунды, `loading` не успевает быть видимым), потом по реальному возрасту данных из HTTP-заголовка `Date` с порогом 60 минут (`useDataFreshness.js` + `getFetchedAt` в `api.js`). Пользователь сообщил, что всё равно не работает.
  4. **Итог: от stale-while-revalidate и от индикации устарелости отказались полностью** — вернулись к простой и предсказуемой схеме "онлайн = только свежее, офлайн = кэш" (текущее состояние). `useDataFreshness.js` и `fetchTimestamps`/`getFetchedAt` в `api.js` удалены. Если снова захочется "быстро из кэша онлайн" — учитывать, что главная проблема не в скорости, а в том, что пользователю невозможно понять, свежие цифры на экране или нет.
- **Обновление данных при переходе на раздел (осталось от захода 2, полезно само по себе):**
  - `Dashboard.jsx` передаёт каждой странице проп `active={key === safeView}` (и общий `isOnline` из `useOnlineStatus.js`, обёртки над `navigator.onLine` + событиями `online`/`offline`). Страницы НЕ размонтируются при переключении разделов (см. комментарий там про `visited`/`display:none`), поэтому именно `active` — единственный сигнал "пользователь только что открыл этот раздел".
  - Паттерн на каждой странице: `useEffect(() => { if (active) loadX(); }, [active, ...остальные зависимости])` — грузим данные заново при каждом переходе на раздел, не только при первом монтировании.
  - Есть состояние `hasData` (взводится в `.finally()` первой загрузки) — отдельно от `loading`, чтобы отличать "первая загрузка вообще, показывать нечего" (полноэкранный "Загрузка...") от "уже есть что показать, просто перезагружаем".
  - Затемнение (`opacity: 0.55`, тот же приём, что у "Обновить сейчас" на Главной) включается по условию `(loading && hasData) || !isOnline` — во время перезагрузки и постоянно, пока нет сети (офлайн данные гарантированно из кэша).
  - Подключено на всех страницах с данными, кроме `Analyst.jsx` (история AI-отчётов, не "дрейфующие" данные — не подключали).
- Так как кэш ключуется по URL без учёта заголовков, `X-Session-Token` в кэш-ключ не попадает — при смене пользователя в одном браузере какое-то время может отдаваться закэшированный ответ, полученный под другим токеном. Для одного магазина с несколькими доверенными сотрудниками это приемлемо, но если появится по-настоящему разный доступ к данным по пользователям — это стоит пересмотреть.
- **Исключение из "кэшируем только GET":** картинки товаров (`POST /api/product-images`, см. `Warehouse.jsx`/`Purchasing.jsx`) на самом деле чтение, а не мутация — POST используется только потому, что список `product_id` может быть длинным и не влезает в query-строку GET. Картинки хранятся как `data:` URL прямо в JSON-ответе (см. `backend/routes/images.js` — файлового хранилища в проекте нет), поэтому закэшировать сам ответ достаточно, отдельно кэшировать байты картинок не нужно. Кэш-ключ для этого запроса — не URL (он один и тот же для любого списка id), а синтетический `Request` с отсортированными id в query-строке (`cacheKeyForProductImages` в `sw.js`) — иначе "Склад" и "Закуп" с разными наборами товаров подменяли бы друг другу картинки из кэша. Загрузка/удаление картинки (`/api/product-images/upload`, `DELETE /api/product-images/:id`) — это уже настоящие мутации, под это исключение не попадают и кэшу не подменяются.
- Т.к. `index.html` не хешируется по содержимому (в отличие от `dist/assets/*.js`/`*.css` от Vite), после деплоя новой версии фронтенда браузер подхватывает новый `sw.js` автоматически при следующем визите (`skipWaiting()` + `clients.claim()` в `activate`), без ручной чистки кэша пользователем.

## Основные фичи и где они живут

### Структура меню (`frontend/src/Sidebar.jsx`)
Пункты сгруппированы по задаче, а не по типу данных (переделано 2026-08-30; до этого 17 пунктов
шли плоским списком в порядке появления страниц, и заголовок был только у "Маркетинга" — один
раздел среди голых пунктов читался как ошибка вёрстки):
- вне групп: **Главная** сверху, **Настройки** внизу перед "Выйти";
- **Деньги** — Отчёт, Расходы, AI Финансист;
- **Продажи** — Заказы, Самовыкупы, География заказов, Проблемные возвраты;
- **Закуп и склад** — Склад, Поставки, Закуп, ABC/XYZ, Юнит-экономика (ABC и юнит-экономика
  отвечают на вопрос "брать ли товар", поэтому живут рядом с закупом, а не с деньгами);
- **Маркетинг** — Реклама товаров, Бонусы от продавца, Бонусы за отзыв.

Правила отрисовки, которые легко сломать при добавлении новой страницы:
- у каждой подстраницы своя иконка (`icon` в `children`), у заголовка раздела — своя; иконки
  живут в объекте `icons` в том же файле, внешних зависимостей нет;
- заголовок раздела — **кнопка**: сворачивает/разворачивает группу, состояние лежит в
  `localStorage` под ключом `sidebar_groups` (только явно свёрнутые; нет ключа = раскрыт);
- если у роли доступна ровно одна страница раздела, заголовок не рисуется — пункт показывается
  как обычный, верхнего уровня (иначе у `manager` было бы четыре заголовка над одиночками);
- в свёрнутом (иконочном) сайдбаре заголовков нет вообще: группы разделены `.sidebar-divider`,
  а все пункты видны всегда, независимо от свёрнутости групп;
- если активная страница оказалась внутри свёрнутого раздела (переход "Закуп → Поставки"
  кнопкой внутри страницы), раздел раскрывается сам; если свернуть его руками, стоя на его
  же странице, он остаётся свёрнутым, а заголовок подсвечивается (`.sidebar-section.has-active`);
- ширина сайдбара 256px и отступ подпунктов 26px подобраны под самое длинное название
  ("Проблемные возвраты"); при добавлении более длинного проверить, что не появилось многоточие;
- у `.sidebar` есть `overflow-y: auto` — без него на невысоком окне нижние пункты уходили
  за край экрана без возможности доскроллить.


### Отчёт / Главная — расчёт чистой прибыли
- `backend/routes/stats.js` — `computeSummaryNetProfit()` считает чистую прибыль на "Главной" за период по ВСЕМ товарам, с **прогнозом** для заказов без загруженного Excel-отчёта Kaspi Pay (берёт средний % прибыли по тому же товару за период, с запасными вариантами: все товары за период → окно 60 дней назад → 0).
- Маркетинг (реклама + бонусы от продавца + бонусы за отзыв) вычитается из чистой прибыли на Главной без прогноза — просто сумма того, что реально загружено (`fetchMarketingTotalForRange`).
- `backend/routes/stats.js` — `/api/stats/product/:productId` (для графика в `ProductDetail.jsx`) теперь тоже прогнозирует чистую прибыль для дней без Excel-отчёта (раньше был разрыв `null`) — использует исторический % прибыли ЭТОГО товара за всю историю. Фронтенд рисует прогнозную часть графика пунктиром (`SalesChart.jsx`, проп `estimatable`).
- ROI везде считается как `Чистая прибыль / (Себестоимость + Маркетинг + Услуги ФФ/Упаковка + Прочие расходы)` — комиссия, доставка и налоги в знаменатель НЕ входят.

### Отчёт: две полные таблицы вместо одной (добавлено 2026-08-30)
На странице "Отчёт" сверху идёт **"Основной отчёт (все склады)"**, под ним — прежний
**"Основной отчёт (Алматы, Астана)"**, ниже без изменений "Общий отчёт" и "Самовыкупы".
Колонки у двух верхних таблиц одинаковые (`MAIN_COLUMNS`), отличается только набор заказов:
- `monthsAll` — `aggregateKaspiPayMonthly()` БЕЗ списка городов: все операции Kaspi Pay, включая
  самовыкупы, заказы с нераспознанной точкой продаж и заказы, которых нет в данных Kaspi вообще.
  Выручка и налог в ней ближе всего к декларации.
- `monthsMainCities` — как было, `MAIN_CITIES` (Алматы + Астана).
- Расходы, не привязанные к городу (маркетинг, упаковка, прочие), подмешиваются обеим таблицам
  одной функцией `withStoreWideExpenses` — раньше этот код жил только в ветке основного отчёта.
- Разбивка по товарам: `GET /api/reports/monthly/:month/products?scope=all` — без `scope`
  отдаёт Алматы + Астану, как раньше. `getProductBreakdownForMonth(month, null)` = все склады.
- **Доли от выручки есть и в разбивке по товарам** (с 2026-08-31): в строке месяца доля считается
  от выручки месяца, в строке товара — от выручки этого товара, поэтому проценты товара и месяца
  не обязаны совпадать. Набор колонок с долями — `PERCENT_OF_REVENUE_KEYS` в `Report.jsx`; там
  перечислены и единый `marketing` (строка месяца), и три товарные колонки
  (`marketing_ads`/`marketing_bonuses`/`marketing_reviews`). Если добавите новую расходную
  колонку — дописать ключ туда, иначе доля под суммой просто не появится.
- **Ловушка при правках фронтенда:** обе таблицы разворачиваемые и делят один кэш разбивок в
  `Report.jsx`, поэтому ключ там составной — `"scope:month"`, а раскрытый месяц хранится по
  таблице (`expandedMonth = { all, main }`). Если сделать ключом просто месяц, в верхней таблице
  покажутся товары нижней.
- **Чего в верхней таблице ждать НЕ надо:** себестоимость (FIFO) считается только по заказам с
  известным складом (`computeCosts` фильтрует `origin_city IS NOT NULL`) — у заказа с
  нераспознанной точкой продаж списывать не с чего. Его выручка в таблицу попадёт, а
  себестоимость нет, поэтому прибыль по таким заказам завышена. И самовыкупы там тоже внутри —
  это осознанно, владелец просил "все заказы", но для оценки реального заработка нужна вторая
  таблица.

### Проблемные возвраты (новая страница, только admin)
Отслеживает заказы, отменённые при доставке Kaspi, и проверяет, не потерял ли их Kaspi/партнёр по фулфилменту.

**Файлы:**
- `backend/kaspiClient.js` — `fetchOrdersByStatus(state, status, dateFromMs, dateToMs, chunkDays)` — ищет заказы Kaspi по state/status за диапазон дат (у Kaspi жёсткий лимит **14 дней** на диапазон creationDate за один запрос — чанкуем). `fetchOrderByCode(code)` — live-статус одного заказа (внутренний id Kaspi = `base64(order_code)`, лукап не нужен).
- `backend/kaspiLogistics.js` — публичный (без токена!) трекинг `https://logistics.kaspi.kz/core/api/public/support?orderId=<код>`.
- `backend/wonderClient.js` — интеграция с партнёром Wonder (принимает физически возвраты/отмены), логин по email/паролю (`WONDER_EMAIL`, `WONDER_PASSWORD` на Render), эндпоинт `https://api.d.wonder-fulfillment.kz/api/refund-order-groups/seller/?page=X&size=Y&status=STATUS` (статусы: `REQUEST`, `WAITING`, `ACTIVE`, `ARCHIVE`).
- `backend/deliveryReturnsSync.js` — вся логика синхронизации (см. ниже).
- `backend/routes/deliveryReturns.js` — `GET /` (список + вычисление "подозрительности"), `POST /sync` (ручной/ночной запуск всех проверок), `DELETE /:orderNumber` (пользователь убирает строку вручную).
- `frontend/src/DeliveryReturns.jsx` — таблица с фильтрами (как на "Заказы"), плюс отдельная таблица снизу для заказов, отменённых ДО передачи в доставку.
- Таблица в БД: `delivery_cancellations` (см. `backend/db.js`).
- Ночной cron в `server.js` (в 03:00): `syncDeliveryCancellations` (последние 2 дня) → `refreshTrackedOrders` → `refreshTrackingStatuses` → `refreshWonderReceived`.

**КРИТИЧЕСКИ ВАЖНЫЕ находки об API Kaspi (наступили на грабли трижды подряд — не повторять!):**
1. `kaspiDelivery.returnedToWarehouse` (в основном Orders API) — **ненадёжное поле**. У реально вернувшегося заказа было `false`. Не использовать как признак "потерян".
2. Верхнеуровневые поля ответа трекинга (`orderStatus`, `active`, `lastActualTrack`) на `logistics.kaspi.kz` — тоже **могут противоречить** собственному массиву `tracks` в том же ответе (пример: `active: true`, `lastActualTrack: null`, но в `tracks` есть `RETURNED` с датой). **Единственный надёжный источник — сам массив `tracks`**: ищем код `RETURNED` (значит точно вернулся), и берём дату САМОГО ПОЗДНЕГО события оттуда.
3. "Активно возвращается" (`tracking_active = true`, применяется порог дней) — определяется ТОЛЬКО если последнее по времени событие в `tracks` начинается с `RETURN_`. Любой другой последний код (`CANCELLED`, `WAITING_IN_PICKUP_POINT`, `WAYBILL_CREATED` и т.п.) — считается разрешённым, не подозрительным, даже если это выглядит как "нет движения давно" — эти заказы просто не проходили полный цикл возврата (например, отменили ещё до отправки).
4. Заказы с последним кодом `CANCELLED` (без единого шага доставки в `tracks`) = отменены ДО передачи в доставку — показываются в ОТДЕЛЬНОЙ таблице снизу, никогда не подозрительны.
5. Порог "подозрительности" (застрял в реальном возврате) = **45 дней** без движения — согласовано с владельцем магазина.

**Про Wonder:** пересечение с нашим списком реальных возвратов (тех, что уехали в доставку) показало, что **~179 из 214** отсутствуют у Wonder вообще — включая заказы с подтверждённым по трекингу Kaspi статусом "RETURNED". Причина не выяснена до конца: либо не все возвраты физически идут через Wonder, либо Wonder теряет часть регистраций. Колонка "Принят складом" (Да/Нет) в таблице просто показывает факт присутствия номера заказа в списке Wonder (`REQUEST`+`WAITING`+`ACTIVE`+`ARCHIVE`), без доп. интерпретации.

### География заказов — `backend/routes/geography.js`, `frontend/src/Geography.jsx`
Страница отвечает на вопрос "где открывать следующий склад". Два уровня разреза: **5 регионов**
(Север, Центр, Запад, Восток, Юг — стандартное экономическое районирование РК) и **20 областей**
(17 областей + Астана, Алматы, Шымкент). Разреза по городам на странице НЕТ и он не нужен —
владелец попросил убрать: решения про склады принимаются на уровне региона и области.
Доступ — admin и marketer.

- **Откуда берутся данные.** Город доставки НЕ хранится отдельной колонкой — он достаётся
  из `orders.raw_data` (полный ответ Kaspi по заказу, который синхронизация сохраняла всегда,
  но до этой страницы никем не читался). Поэтому историю не пришлось перекачивать: карта
  сразу работает по всем ранее загруженным заказам. Основное поле — `attributes.deliveryAddress.town`,
  с запасными вариантами и разбором `formattedAddress` до первой запятой.
- **Расходы на доставку берутся из `attributes.deliveryCostForSeller`** в `raw_data` — это
  ровно то, что Kaspi списывает с продавца за доставку заказа. Поле есть у 100% заказов, тогда
  как Excel-отчёт Kaspi Pay загружен примерно у 84%. Сверено на живых заказах: 1507 / 927 / 1971 ₸
  в `deliveryCostForSeller` совпали с колонкой доставки в Excel до тенге. Сумма по Excel всё
  равно считается и лежит в ответе как `coverage.reportDeliveryCost` — контрольная цифра на
  случай расхождений. Не путать с `attributes.deliveryCost` — это то, что платит ПОКУПАТЕЛЬ.
- **`DELIVERY_PICKUP` — это НЕ "самовывоз от продавца".** Проверено на живом заказе: заказ
  из Алматы в Караганду с `deliveryMode = DELIVERY_PICKUP` и `isKaspiDelivery = true` стоил нам
  1507 ₸ доставки — то есть до пункта выдачи его вёз Kaspi, а покупатель просто забрал сам.
  Настоящий самовывоз от продавца — тот же режим, но с `isKaspiDelivery = false`, и таких
  единицы. В августе 2026 это была половина всех заказов (100 из 195), так что ошибка в
  подписи здесь стоит дорого. В реальных данных встретились только три режима:
  `DELIVERY_PICKUP`, `DELIVERY_REGIONAL_TODOOR`, `DELIVERY_LOCAL`.
- **Улица и координаты в адресе есть только у СВОЕЙ доставки.** У заказов Kaspi Delivery
  `deliveryAddress` заполнен одним `town` — ни улицы, ни координат (это видно и по
  `/api/geography/fields`, который считает только непустые значения). Поэтому определять область
  по координатам можно лишь как запасной вариант — зато срабатывает он как раз там, где нужен:
  у своей доставки в адресе стоят мелкие сёла, которых нет в справочнике.
- **Область определяется в три шага** (`resolveRegion` в `backend/kzRegions.js`): подсказка
  Kaspi в скобках → справочник городов → координаты (`backend/kzRegionShapes.js`, точка в
  полигоне). Подсказка идёт первой не случайно: Kaspi часто пишет город как
  "Кайнар (Жамбыл.обл.)" или "Юбилейное(Карг.Обл)", и именно так выяснилось, что Юбилейное —
  карагандинское, а не северо-казахстанское, как было в справочнике сначала.
- **Справочник `backend/kzRegions.js`** — ~300 населённых пунктов с казахскими написаниями
  ("Ақтөбе" и "Актобе" — одна строка). Незнакомый пункт не теряется молча: он попадает в блок
  "Не удалось определить область" внизу страницы, оттуда его и надо дописать в справочник.
  Спорные омонимы (Актау, Есиль, Абай, Федоровка, Аксу, Достык, Каратал, Шар) разрешены явным
  списком в конце файла — не переставляй их случайно.
- **Справочник сверен с geonames** (там у каждого населённого пункта есть код области, включая
  коды областей 2022 года). Из ~290 названий разошлись три, ошибкой оказалось одно — Леденево.
  Той же сверкой разложены города по новым областям: Абайская, Жетысуская и Улытауская.
  Скрипт жил во временной папке, но повторить просто: взять `KZ.txt` с download.geonames.org,
  сопоставить колонку admin1 с областями (01 Алматинская, 02 Алматы, 03 Акмолинская,
  04 Актюбинская, 05 Астана, 06 Атырауская, 07 ЗКО, 08 Байконур, 09 Мангистауская,
  10 Туркестанская, 11 Павлодарская, 12 Карагандинская, 13 Костанайская, 14 Кызылординская,
  15 ВКО, 16 СКО, 17 Жамбылская, 1537272 Шымкент, 12510143/144/145 — Абайская/Жетысуская/
  Улытауская) и сравнить с `CITY_TO_REGION`. Осторожно: население в geonames по казахстанским
  сёлам почти везде 0, выбрать "самый крупный из одноимённых" по нему нельзя — Каргалы в базе
  девять штук.
- **Карта — сгенерированный файл `frontend/src/kazakhstanMap.js`, руками не правится.**
  Контуры взяты из **OpenStreetMap** (ODbL) через Overpass API, упрощены и спроецированы заранее
  (никаких картографических библиотек в бандле, ~27 КБ). Сначала карта строилась по Natural
  Earth и geoBoundaries — обе дают деление ДО 2022 года, всего 14 областей, из-за чего на карте
  не было Абайской, Жетысуской и Улытауской. В OSM деление актуальное, поэтому теперь на карте
  честные 17 областей. Если понадобится перегенерировать: Overpass-запрос — все отношения
  `boundary=administrative` + `admin_level=4` внутри `ISO3166-1=KZ`, дальше границы приходят
  набором линий в произвольном порядке, их надо склеить в замкнутые контуры по совпадающим
  концам.
- **Подсказка на карте гасится по `onMouseOut` самой `<svg>`, а не по `onMouseLeave` карточки.**
  Карточка шире страны (море, соседние государства, поля по краям), поэтому при уходе курсора
  с области в пустоту внутри карты `mouseleave` не срабатывал и подсказка оставалась висеть.
  В обработчике проверяется `relatedTarget`: если курсор ушёл на другую область — не гасим,
  её собственный `onMouseEnter` тут же поставит новое значение (иначе подсказка моргала бы при
  переходе между соседними областями). Клик по фону карты снимает "прикреплённую" тапом
  подсказку — она нужна на телефоне, где наведения нет.
- **Подсветка региона при наведении рисуется хитростью, а не обводкой контура.** Своей
  геометрии у региона нет — есть только области, а объединять полигоны в браузере дорого и
  на упрощённых контурах даёт щели. Поэтому сначала рисуется толстая обводка по ВСЕМ областям
  региона, а поверх — их же заливки: обводка идёт по центру линии, внутренние границы
  закрываются заливками соседей с обеих сторон, снаружи остаётся ровно контур региона.
  Заливка полупрозрачная, поэтому под цвет подкладывается непрозрачный фон карточки.
  Слою подсветки обязателен `pointer-events: none` — иначе курсор, наехав на неё, терял бы
  область под ней и подсказка мигала.
  Отдельная деталь: правило `.kz-map.by-macro .kz-region` перебивает по специфичности
  `.kz-region.active`, из-за чего в режиме регионов подсветка сначала вообще не работала.
- **Города республиканского значения рисуются кружками, а не контурами.** В режиме регионов
  кружки не рисуются вовсе: город и так часть своего региона, а одинокий кружок поверх
  сплошной заливки (Астана в Северном) выглядит мусором. Их площадь на карте
  страны вырождается в точку, а заказов туда идёт больше, чем в иные области.
- **Шкала цвета областей считается без городов республиканского значения.** Алматы и Астана
  почти всегда крупнее любой области, а на карте они всего лишь кружки — если брать максимум
  по ним, все области красятся в один средний оттенок и карта перестаёт что-либо показывать.
  В режиме регионов области одного региона заливаются одним цветом, а границы между ними
  делаются бледными — так пять регионов читаются как цельные куски.
- `backend/kzRegionShapes.js` — тоже сгенерированный файл, но это НЕ карта: там контуры
  областей в градусах и только для проверки "точка внутри области". Контуры упрощены до ~5 км,
  поэтому у точки на самом краю (Актау стоит прямо на берегу Каспия) есть запасной вариант —
  ближайшая область в радиусе 0.6°.
- **Диагностика:** `GET /api/geography/fields` показывает, какие поля Kaspi реально кладёт в
  заказ (только имена полей и доли заполненности непустыми значениями, без самих адресов).
  Плюс в ответе основного роута есть `coverage` — по какой доле заказов вообще известен город;
  если он ниже 50%, страница честно пишет об этом баннером, а не рисует пустую карту.

### ABC/XYZ (что закупать в первую очередь) — `backend/routes/abc.js`, `frontend/src/AbcXyz.jsx`
Товарная матрица в двух измерениях: ABC — вклад товара в прибыль (или в выручку, переключателем),
XYZ — насколько ровно он продаётся по неделям. Доступ только admin. Период по умолчанию — 90 дней:
на коротком отрезке стабильность спроса считать не по чему.

- **Прибыль считается тем же движком, что и на Главной.** `computeCostsByOrderItem` (FIFO по
  партиям) вынесена в экспорт из `routes/stats.js` и переиспользуется — дублировать этот расчёт
  нельзя, иначе прибыль на двух страницах разъедется. Комиссия и доставка делятся между товарами
  заказа пропорционально их доле в чеке, как в "Отчёте". По заказам без загруженного Excel-отчёта
  Kaspi Pay прибыль оценивается по среднему проценту ЭТОГО ЖЕ товара; если оценки больше 20%
  выручки, страница пишет об этом баннером.
- **Маркетинг вычитается по товарам** (`campaignCostByProduct`) — та же логика, что в "Отчёте"
  (стоимость кампании делится поровну между её товарами), но по датам, а не по месяцу.
- **Пороги XYZ — 25% и 50%, а НЕ классические 10% и 25%.** Классические придуманы для складов,
  отгружающих сотни одинаковых единиц в неделю. На живых данных за июнь–август 2026 при них ВСЕ
  товары до единого попали в Z — включая те, что продавались все 13 недель из 13 без единого
  пропуска: реальные коэффициенты вариации там от 38% до 122%. Если однажды покажется, что "почти
  всё в Z" — это не баг, а особенность маркетплейса: спрос скачет из-за акций и рекламы. Колонка
  "недель с продажами" в таблице как раз отделяет "продаётся ровно" от "продаётся рывками".
  Пороги отдаются фронтенду в поле `thresholds`, подписи под матрицей берутся оттуда — менять
  их надо в одном месте, в `abc.js`.
- **Товару с малым объёмом класс XYZ не присваивается вообще** (меньше 6 недель в периоде или
  меньше 6 проданных штук) — считать стабильность спроса по двум продажам самообман. Такие товары
  попадают в отдельный столбец "мало данных", а не в Z.
- **Знаменатель ABC — сумма только ПОЛОЖИТЕЛЬНЫХ вкладов.** Иначе один крупный убыток разгонял бы
  накопленную долю прибыльных товаров за 100%. Убыточный товар не попадает в группу A ни при какой
  накопленной доле.

### Юнит-экономика (стоит ли брать товар) — `backend/routes/unitEconomics.js`, `frontend/src/UnitEconomics.jsx`
Калькулятор ДО закупки, в отличие от всех остальных страниц, которые считают факт. Вводишь цену,
вес, курс, ставку карго и режим ввоза — видишь маржинальность, прибыль с партии, ROI и цену,
ниже которой падать нельзя. Доступ только admin.

- **Считает целиком на фронте, бэкенд нужен только за исходными данными.** `GET
  /api/unit-economics/defaults` отдаёт то, что не надо вбивать руками: реальную комиссию Kaspi
  и реальную стоимость доставки (по собственным продажам за 90 дней), последние курсы валют
  из партий и список товаров с их закупочными ценами — чтобы можно было начать расчёт от
  реального товара. На август 2026 это 12.61% комиссии и 1 434 ₸ доставки на штуку.
- **Подставляются только ПУСТЫЕ поля.** Если человек уже что-то ввёл руками, ответ сервера это
  не перетирает — иначе набранный расчёт слетал бы при каждом перезаходе на страницу.
- **Ввод сохраняется в localStorage** (`unit_economics_input`): расчёт часто бросают на середине.
  Чтение и запись обёрнуты в try/catch — приватный режим браузера может запрещать запись.
- **Формулы.** Всё считается на одну штуку, на партию умножается в конце. Таможенная стоимость
  (для пошлины и НДС) = закупка + доставка до границы. НДС при импорте на упрощёнке к зачёту
  НЕ берётся — это чистый расход, о чём написано прямо под полем. ROI считается по той же
  формуле, что и везде в дашборде: прибыль делить на вложения в товар (закупка + логистика +
  ввоз + переменные + реклама), комиссия/доставка/налоги в знаменатель не входят.
  "Цена в ноль" — это решение уравнения, а не сумма расходов: комиссия, реклама и налог сами
  зависят от цены.
- **И закупка, и логистика вводятся суммой за ПАРТИЮ** с выбором валюты и курсом, а под полем
  показывается, сколько это выходит на штуку. Поставщик и карго выставляют счёт за партию, и
  делить его на количество в уме продавцу не нужно.
- **Список товаров идёт БЕЗ фильтра по складу, а цена продажи и ДРР — по основному магазину.**
  Разделять обязательно: утюжок HS-918 продавался только самовыкупами и из-за фильтра вообще
  не появлялся в списке, а когда фильтр убрали целиком, самовыкупы попали в среднюю цену и
  уронили её (HY320 с 24 191 ₸ до 18 076 ₸, LUMIX HD с 52 256 ₸ до 33 485 ₸) — самовыкуп это
  покупка у самого себя, часто по акционной цене. Для товаров, которые шли ТОЛЬКО самовыкупами,
  цена берётся по всем складам, иначе её не было бы вовсе.
- **Свои товары**, которых ещё нет в продажах, заводятся кнопкой "Новый товар": id генерируется
  как `custom:<время>`, название хранится в `unit_economics_presets.product_name` — больше его
  взять неоткуда. Пока расчёт не сохранён, такой товар живёт только в состоянии страницы.
  В список также попадают сохранённые расчёты по товарам, выпавшим из окна 90 дней, — иначе
  расчёт остался бы в базе, а добраться до него из интерфейса было бы нельзя.
- **Сохранённые расчёты по товарам** лежат в таблице `unit_economics_presets` (одна строка на
  товар, форма целиком в JSONB), а не в localStorage: считают за компьютером, а проверяют
  с телефона. Выбрал товар — если по нему сохраняли, форма подставляется целиком; не
  сохраняли — работает подстановка из закупочных цен. У сохранённых товаров в списке галочка.
- **ДРР товара показывается подсказкой под полем "Реклама", но в поле НЕ подставляется**
  (владелец попросил именно так 2026-08-29): реклама в расчёте перед закупкой — это план на
  будущее, а факт прошлых 90 дней нужен только для сверки. Считается как расходы на рекламу
  этого товара за окно, делённые на его выручку — ровно то же число, что на карточке "ДРР за
  период" страницы "Реклама товаров" (сверено: LUMIX HD за 30 дней — 8 233 ₸ рекламы на
  1 478 500 ₸ выручки = 0.56%, карточка показывает 0.6%; за 90 дней у того же товара 0.67%).
- **Окно ДРР скользящее и считается на каждой загрузке страницы**, а не замораживается при
  сохранении расчёта: в пресете лежат только введённые поля, подсказка приходит из
  `/api/unit-economics/defaults` со свежим `now() - 90 days`. Кэш service worker тут ничего не
  портит — он network-first и достаётся только офлайн. Но сами расходы на рекламу заливаются
  вручную Tampermonkey-скриптом, поэтому ДРР свежий ровно настолько, насколько свежа последняя
  выгрузка кампаний.
- **Пошлина и НДС заполняются двумя способами** (добавлено 2026-09-06): процентом, как было,
  либо готовой суммой ЗА ПАРТИЮ — её берут прямо из документов брокера, где всё уже посчитано.
  Под каждым из двух полей тумблер "заполнить вручную" (`dutyMode`/`vatMode` = `percent|manual`),
  сумма лежит в отдельных полях `dutyAmountPerBatch`/`vatAmountPerBatch`, поэтому переключение
  режима туда-обратно ничего не стирает. Единица "за партию" выбрана осознанно — так же введены
  соседние Брокер/СВХ/Сертификация, и так их выставляет брокер; на штуку делится в `calculate`.
  Важная деталь: **НДС в процентах считается от таможенной стоимости ПЛЮС пошлина**, поэтому при
  ручной пошлине база у процентного НДС меняется — так и задумано (проверено: пошлина 400 000 ₸
  на партию в 500 шт даёт 800 ₸/шт и поднимает НДС с 1 361 до 1 388 ₸/шт).
  Старые сохранённые расчёты без этих полей считаются процентами, как раньше — `EMPTY_FORM`
  подставляет `percent` по умолчанию, миграция не нужна.
- **Маркетинг разбит на три поля** под названиями разделов из меню: "Реклама" и "Бонусы от
  продавца" — проценты от цены продажи, "Бонусы за отзыв" — фиксированная сумма в тенге с
  продажи (за отзыв платят деньгами, а не долей чека). Это важно для расчёта цены
  безубыточности: проценты входят в делитель уравнения, а фиксированная сумма — в числитель.
- **При переименовании полей формы нужна миграция в `migrateForm`.** Набор полей меняется, а
  сохранённые расчёты остаются со старыми ключами, и поле молча оказывается пустым — человек
  решит, что расчёт потерялся. Так было при переходе цены закупки с "за штуку"
  (`purchaseForeign`) на "за партию" (`purchaseAmount`): старое значение умножается на
  количество. Ключ при смене СМЫСЛА поля надо именно переименовывать, а не оставлять прежним:
  цена за штуку, молча прочитанная как цена за партию, дала бы прекрасную маржу и неверное решение.
- **Логистика вводится суммой за партию** (было: вес и ставка за килограмм) (владелец попросил так 2026-08-29): карго выставляет счёт именно за партию, и
  пересчитывать его в ставку за кг продавцу пришлось бы вручную. Так же логистика записана и
  в "Поставках" (`logistics_currency`/`logistics_amount_foreign`/`logistics_rate`), поэтому
  подстановка из своего товара берёт цену за штуку из последней партии и умножает на количество
  ИЗ ТЕКУЩЕГО расчёта, а не на количество той поставки.
- **Проверено на живом товаре** (Проектор TOMMILI LUMIX HD, закупка 68.73 $ по 466 ₸, логистика
  450 000 ₸ на партию в 100 шт): в серую — прибыль 6 137 ₸ со штуки, маржа 11.7%, ROI 16.8%,
  цена в ноль 44 984 ₸. В белую с пошлиной 5% и оформлением 310 000 ₸ на партию тот же товар
  уходит в минус на 3 392 ₸ со штуки. Цифры сошлись с расчётом на бумаге до тенге. Та же сумма
  логистики, введённая в долларах (965.67 $ по 466), даёт тот же результат.
- **Полоса "структура цены" нормируется по сумме самих полос, а не по цене.** При убытке расходы
  больше цены, доли от цены дали бы в сумме больше 100%, и полоса поехала бы; вместо прибыли
  рисуется красный сегмент "не хватает до нуля".
- **Про вёрстку:** колонки страницы заданы через `minmax(0, 1fr)`, а не `1fr`. У обычного `1fr`
  минимум равен содержимому, и таблица "Статьи расходов" растягивала колонку до 480px на экране
  в 375px — поля уезжали за край экрана. Тот же приём нужен любой будущей странице, где внутри
  грида лежит таблица.

### Склад / Поставки / Закуп (снабжение)
- И "Склад", и "Поставки" рендерят отдельную таблицу на каждый город (Алматы/Астана/...), а не одну общую со столбцом "Склад" — паттерн: сгруппировать по `warehouse`, отсортировать города через `localeCompare(..., 'ru')`, на каждую группу свой `<div className="section-title">{city}</div>` + `<div className="card">`.
- **Склады описаны в ОДНОМ месте — `backend/warehouseMapping.js`.** Там массив `WAREHOUSES`: код точки продаж Kaspi (`pickupPointId`), город, роль (`main` — идёт в «Основной отчёт» и на Главную, `selfbuy` — считается отдельно) и `display` (показывать ли на «Складе»). Все прочие списки (`ALL_CITIES`, `MAIN_CITIES`, `SELF_BUY_CITIES`, `DISPLAY_CITIES`, `CITY_ORDER`, `PICKUP_POINT_WAREHOUSE_MAP`) выводятся из него автоматически. **Чтобы добавить склад — допиши одну строку**, больше ничего править не нужно; фронтенд получает список складов с сервера в ответе `GET /api/batches`, своей копии не держит. До 2026-08-29 эти сведения были размазаны по восьми спискам в шести файлах и успели разъехаться: «основной магазин» на Главной означал «всё, кроме самовыкупов» (то есть включал заказы без склада), а в «Отчёте» — «ровно Алматы и Астана». Теперь оба экрана спрашивают `MAIN_CITIES` у справочника.
- **Заказ с неизвестной точкой продаж больше не пропадает молча.** Если Kaspi заведёт новую точку, её кода не будет в справочнике, `origin_city` станет `NULL`, и заказ выпадет из «Отчёта», со «Склада» и из расчёта себестоимости. `GET /api/orders` возвращает `unknownPickupPoints` (код точки, число заказов, диапазон дат), а страница «Заказы» показывает по ним предупреждение — видно, какую строку дописать в справочник. Миграция в `db.js` при каждом старте пересчитывает `orders.origin_city` из сохранённого `pickup_point_id`, поэтому добавление склада чинит и уже загруженные заказы задним числом.
- `product_batches.status` — `'received'` (по умолчанию, физически на складе) или `'in_transit'` (заказано у поставщика, ещё в пути). `computeWarehouseStock()` в `backend/routes/warehouse.js` считает FIFO-остаток **только** по `status='received'` — in_transit-партии в реальный остаток склада не входят. Кнопка "Отметить прибывшим" (`POST /api/batches/:id/receive`) переводит статус в received и проставляет `received_date = сегодня`.
- **Товар в форме поставки можно ввести вручную** — для нового товара, у которого карточка на Kaspi уже есть, а продаж ещё не было (значит и в `order_items` его нет). Ключевое поле — **артикул** (`product_id` = `offer.code` из заказа Kaspi): это единственное, что связывает партию с продажами при FIFO-списании, и **ошибка в нём не вызывает никакой ошибки** — партия просто сохранится и никогда ни с чем не свяжется. Артикулы бывают двух видов: простые числа (`426553`) и составные через подчёркивание (`116138814_302817922`, там где Kaspi не отдал `offer.code` и подставился запасной идентификатор), — заранее угадать формат нельзя. Поэтому `GET /api/batches/products` возвращает флаг `from_sales`, а в выпадающем списке товары без продаж помечены: если пометка осталась после первой продажи — артикул набран неверно.
- **Партиями пользуются не только как партиями товара.** В примечаниях встречаются «Депозит у поставщика 3000 USD» (партия из 1 шт по 1 464 000 ₸) и «Разбор возвратов» (20 шт по 0,1 ₸). Пока такая партия `in_transit`, FIFO её не трогает, но при «Отметить прибывшим» она отравит себестоимость товара — именно это дало заказу 1047398639 маржу −2009%. **Перед приёмкой партии всегда смотри её `note` и сравнивай `cost_price` с медианой по этому товару.** Отдельного места для «депозит поставщику» в приложении нет — это расход, а не товар.
- **Фильтр `status = 'received'` обязателен ВЕЗДЕ, где считается FIFO — а копий формулы три.** Кроме `computeWarehouseStock()` это `computeCosts()` в `backend/costEngine.js` (себестоимость по заказам и месяцам) и в `backend/routes/stats.js` — `computeCostsByOrderItem()` (разбивка по товарам в "Отчёте") и `computeProductDailyCost()` (дневной график товара). До 2026-08-28 фильтра не было ни в одной из этих трёх: FIFO, исчерпав прибывшие партии, молча переходил на партию "в пути" и брал её цену. Заказ 1047398639 (Проектор TOMMILI LUMIX HD, выручка 69 900 ₸) оказался 114-й проданной единицей при 113 прибывших и получил себестоимость 1 464 000 ₸ с ещё не приехавшей партии — маржа −2009%. Симптом узнаваемый: **одна и та же партия одновременно "не в остатке" на Складе и "продана" в Отчёте**. Если будешь добавлять четвёртое место с FIFO — фильтр не забудь.
- **Oversold (продано больше, чем приехало) оценивается по цене ПОСЛЕДНЕЙ прибывшей партии.** Раньше такая часть продажи оставалась вообще без себестоимости, и заказ показывал прибыль, равную всей выручке — это хуже любой оценки. Оценка самоисправляющаяся: FIFO считается с нуля при каждом вызове, поэтому как только партия отмечена прибывшей (`received_date = сегодня`, то есть она встаёт в конец очереди FIFO), те же продажи пересчитываются по её настоящей цене. Реализовано во всех трёх копиях FIFO. **Если прибывших партий нет вообще** (весь товар ещё в пути) — себестоимость остаётся неизвестной; цену партии "в пути" не берём даже как оценку, именно это было багом заказа 1047398639.
- На "Поставках" столбец "Остаток" (`remaining_quantity`) убран из таблицы — это поле не уменьшается продажами (см. предупреждение в `warehouse.js` выше), почти всегда совпадает с "Заявлено" и вводило в заблуждение. Настоящий остаток — только на "Складе".
- Даты на "Поставках" — через `formatDateDMY()` из `dateUtils.js` (DD/MM/YYYY); при редактировании поставки `received_date` из базы (полный ISO-таймстамп) нужно резать до `slice(0,10)` перед тем, как класть в `<input type="date">`, иначе поле останется пустым.
- **Калькулятор валюты в форме поставки** — `purchase_price`/`logistics_cost` в базе всегда в ₸ за 1 шт (это единственное, что участвует в расчёте себестоимости и `cost_price`). Поставщикам обычно платят в $ или ¥, логистику — то в ₸, то в $, поэтому в форме есть два блока-калькулятора выше итоговых полей: "Сумма закупки за партию" + валюта (₸/$/¥) + "Курс", и "Логистика за партию" + валюта (₸/$) + "Курс" — каждый умножает сумму на курс, делит на количество и подставляет результат в поля "...за 1 шт, ₸". **Эти итоговые поля — не `input`, а нередактируемые значения** (`.batch-computed-value`): их просили сделать «только для информации», чтобы посчитанное нельзя было случайно разойтись с введённым. Из-за этого у формы нет HTML-валидации `required` на цене, поэтому в `handleSubmit` стоит ручная проверка «цена за 1 шт ещё не рассчиталась». Когда выбрана валюта ₸, поле "Курс" отключается (курс = 1). Сумма/валюта/курс дополнительно сохраняются в БД (`purchase_currency`, `purchase_amount_foreign`, `purchase_rate`, `logistics_currency`, `logistics_amount_foreign`, `logistics_rate` — все nullable) чисто как справочная информация для истории, в формулах себестоимости не участвуют. У партий, добавленных до этой фичи (или где калькулятор не использовался), эти поля `NULL`.
- **Форма поставки разбита на смысловые блоки** (`.form-section` + `.form-section-title` + `.form-section-hint` в `Batches.jsx`/`styles.css`), порядок фиксированный и осмысленный: **Товар → Партия → Закупка → Логистика → Прочие расходы → Себестоимость за 1 шт → Примечание**. Полей в форме ~14, без блоков на телефоне это сплошная лента. Разделители — тонкие линии (`border-top`), а не вложенные рамки: модалка и так на `--bg-card`, поля на `--bg`, третий уровень вложенности выглядел бы тяжело. Исключение — итоговый блок `.form-section-result`, он специально выделен фоном как результат.
  - **"Количество" стоит в блоке "Партия", то есть ВЫШЕ блоков с суммами** — это не косметика: обе суммы (и прочие расходы) делятся именно на количество, и спрашивать его последним было логически неправильно.
  - Итоговая строка (`.batch-result-row`) — `auto-fit`-сетка, потому что значений то 3, то 4: колонка "Прочие" появляется только когда прочие расходы реально заполнены.
- **Прочие расходы на партию (сертификаты, НДС, растаможка, ...)** — произвольный список строк `{ name, amount, currency, rate }`, названия придумывает пользователь. Хранятся в `product_batches.extra_expenses` (JSONB, nullable) — не отдельными колонками и не отдельной таблицей, потому что длина списка заранее неизвестна, а выбирают их всегда вместе с самой партией, join не нужен. Суммы указываются за ВСЮ партию (как закупка и логистика), а в `cost_price` попадают уже поделёнными на количество.
  - **Это влияет на деньги во всём приложении:** `cost_price` = закупка/шт + логистика/шт + прочие/шт, а `cost_price` — единственный источник себестоимости для FIFO-списания (`costEngine.js`), оценки склада (`warehouse.js`) и расчёта прибыли (`stats.js`). То есть прочие расходы автоматически уменьшают показываемую прибыль. Пересчёт происходит только при сохранении партии — у поставок, созданных до появления этой фичи, `extra_expenses` = `NULL` и `cost_price` не меняется.
  - Валидация — `normalizeExtraExpenses()` в `backend/routes/batches.js`: строки без названия или без суммы молча отбрасываются (это необязательная часть формы, одна пустая строка не должна ронять сохранение всей поставки), название режется до 60 символов, список — до 20 строк, для `KZT` курс всегда принудительно 1, для остальных валют забытый курс превращается в 1 (а не в 0, иначе расход бесследно исчез бы из себестоимости).
  - **Условия отбора строк продублированы на фронтенде** (`filledExpenses` в `Batches.jsx`) — специально совпадают с бэкендом, иначе предпросмотр "Себестоимость за 1 шт" в форме разошёлся бы с тем, что реально сохранится. Если менять правила отбора — менять в обоих местах.

### "Деньги в товаре" (добавлено 2026-08-31) — `GET /api/warehouse/inventory-value`
Сколько денег лежит в товаре: блок из трёх карточек наверху "Склада" + плитка на Главной.
Считает `computeInventoryValue()` в `backend/routes/warehouse.js`, оба места берут один роут.
- **На складе** — остаток по FIFO × себестоимость, по ВСЕМ складам, включая самовыкупные.
  Это НЕ то же, что "Итого" под таблицей города: там только Алматы и Астана (`display: true`),
  и суммы разбиты по городам. Разбивка по складам возвращается в `stock_by_warehouse`.
- **В пути** — по партиям `status='in_transit'`, по ПОЛНОЙ себестоимости (`cost_price` = закупка +
  логистика + прочие расходы), а из чего она состоит, написано в подписи под цифрой
  (`in_transit_purchase` и `in_transit_extra` = `(cost_price − purchase_price) × quantity`).
  Сначала логистика в `total` не входила (логику "считаем только то, что уже заплачено за сам
  товар" предложила я, владелец согласился), но 2026-09-01 он указал на ошибку: карточка
  "На складе" считается по `cost_price`, то есть логистика в остатке уже учтена, и капитал
  из-за этого был занижен на 570 637 ₸. **Обе части теперь считаются одинаково** — если
  соберётесь снова что-то вычитать из одной, проверьте, что то же самое вычтено из другой.
- **Депозиты и авансы поставщику** заводят той же формой поставки (партия из 1 шт по 1 464 000 ₸
  с примечанием "Депозит у поставщика 3000 USD"), отдельного признака у партии нет. Поэтому они
  вычисляются по регулярке `DEPOSIT_NOTE_RE` (депозит|аванс|предоплат) в примечании и показываются
  строкой "в том числе" внутри "В пути" — деньги отданы, из суммы их не выкидываем. Если решите
  делать нормальный признак у партии — менять здесь и в форме на "Поставках".
- `total` = остаток склада + полная стоимость партий в пути. Проверено на подставной базе:
  остаток считается FIFO с учётом продаж, самовыкупный склад не теряется, закупка и логистика
  складываются в `in_transit_value` и обе попадают в `total`.
- На Главной плитка не показывается в режиме самовыкупов (`mode === 'selfbuy'`) — цифра общая по
  магазину и среди самовыкупных продаж читалась бы как их собственная. Ряд карточек там при этом
  переключается на класс `.stats-row-inventory` (`auto-fit, minmax(230px, 1fr)`): при жёстких
  пяти колонках на ноутбуке сумма переносилась на вторую строку, а бейдж "⌀ N/день" наезжал на подпись.

### Закуп (планирование пополнения) — `backend/routes/purchasing.js`, `frontend/src/Purchasing.jsx`
Страница под "Складом" (только admin), список товаров с рекомендацией "сколько и когда закупать". Считается по классической модели **(s, S)**:
- `s` (точка заказа) = Прод./день × `lead_time_days` × (1 + `buffer_pct`/100) — порог для статуса Критично/Скоро.
- `S` (уровень пополнения) = `s` + Прод./день × `lead_time_days` — цель, до которой считается "К закупу" (`Math.ceil(S − остаток)`), **независимо от того, ниже ли остаток точки s** — поэтому "К закупу" может быть > 0 даже когда остаток уже выше точки заказа. Это НЕ проверено против реального стороннего инструмента с того скриншота, откуда бралась идея страницы — формула подобрана так, чтобы сошлись 3 примера чисел с скриншота, но это реконструкция, а не подтверждённый факт. Если пользователь скажет, что цифры "не такие", это первое, что нужно перепроверить.
- Статус: Критично — дней остатка < `lead_time_days`; Скоро — < `lead_time_days × 1.5` (тоже собственное предположение, порог с скриншота не восстанавливался); иначе В норме.
- Прод./день = среднее за последние 30 дней (`order_items` за `VALID_STATUSES`, см. `warehouse.js`).
- `lead_time_days`/`buffer_pct` — настраиваются в UI ("Настройка параметров"), хранятся в отдельной синглтон-таблице `purchasing_settings` (id=1, дефолт 14 дней / 30%).
- "Доступно" на этой странице — разбивка по ВСЕМ 4 складам (в отличие от "Склада", который сознательно показывает только Алматы/Астана).
- "Экспорт Excel" на самом деле CSV (не добавляли новую зависимость типа `xlsx` в frontend) — открывается в Excel нормально, просто не .xlsx.

Если скрипт снова начнёт падать с 404 на каком-то из трёх разделов — первым делом сверить версию в упавшем URL с версией у соседних функций того же раздела в скрипте.
- Токен дашборда внутри скрипта (`GM_setValue('dashboard_token', ...)`) не имеет автообновления — если начнутся 401 "Сессия истекла" при выгрузке, у пользователя не включён Advanced-режим в Tampermonkey (не видно вкладки Storage/Values), поэтому проще всего временно добавить `GM_setValue('dashboard_token', '');` перед `getDashboardConfig()`, сохранить, дать скрипту заново спросить токен через `prompt()`, затем эту строку убрать.
- В "Основной отчёт" все три источника суммируются в одну колонку "Маркетинг"; в разбивке по товарам — три отдельные колонки.
- **По бонусам от продавца тянем не только расход** (с 2026-09-06). Дневной эндпоинт
  `.../bonuses/products/api/v1/merchant/{id}/overview/campaign/{cid}/daily` **без метрики в пути**
  отдаёт сразу всё: `{date, views, clicks, favorites, carts, transactions, gmv, bonusAmount}`.
  Раньше скрипт ходил в вариант `/daily/bonusAmount` и приносил только сумму. Пути с метрикой
  существуют не для всех показателей — `/daily/views`, `/daily/clicks`, `/daily/favorites`,
  `/daily/transactions` отвечают 200, а `/daily/gmv`, `/daily/orders`, `/daily/cart` — 404,
  так что общий `/daily` единственный способ забрать всё разом (проверено запросами в консоли
  браузера 2026-09-06; v2 и v3 этого раздела не существует, только v1).
  Те же поля лежат и в списке кампаний `/campaigns` — суммой за период, поэтому скрипт по ним
  отсеивает акции без активности, не тратя запросы.
- **Метрики в `bonus_expenses` необязательные, и это важно.** В `/upload` каждое поле дня, кроме

- На странице "Бонусы от продавца" эти цифры показываются карточками (продажи, заказы, отдача

  блоки включаются по факту наличия ненулевых данных (`hasFunnel`), а не по названию страницы.

## Сетевые запросы фронтенда (`frontend/src/api.js`)

- **У каждого запроса есть таймаут (`AbortController`), и это обязательно.** Было расследование (2026-08-24): пользователь нажал "Сохранить" в форме поставки, кнопка навсегда залипла на "Сохраняем...", помогла только полная перезагрузка приложения. Причина: `fetch` без таймаута на подвисшем мобильном соединении (сеть переключилась, сокет открыт, ответа нет, ошибки тоже нет) **никогда не резолвится и не реджектится** — значит `.finally(() => setSaving(false))` не выполняется ВООБЩЕ, и форма остаётся заблокированной навсегда. Теперь: `DEFAULT_TIMEOUT_MS = 45 с` (с запасом на просыпание Render после простоя), `LONG_TIMEOUT_MS = 5 мин` для тяжёлых операций — `/api/sync`, `/api/expenses/sync`, `/api/delivery-returns/sync`, загрузка Excel и картинок, генерация AI-отчёта, `/api/reports/delivery-anomalies`. Если добавляется новый долгий эндпоинт — не забыть передать ему `{ timeoutMs: LONG_TIMEOUT_MS }`, иначе он будет обрываться на 45-й секунде.
- Таймер снимается в `finally` только ПОСЛЕ чтения тела ответа — зависнуть можно не только в ожидании заголовков, но и на середине чтения.
- Сетевые сбои `fetch` кидает как `TypeError` с техническим текстом ("Load failed"/"fetch failed") — он перехватывается и заменяется на понятную фразу. `UNAUTHORIZED` пробрасывается как есть: на него завязан автоматический выход из аккаунта в `App.jsx`.
- `login()` ходит мимо `apiRequest` (токена ещё нет), поэтому таймаут ему прописан отдельно — иначе точно так же залипал бы экран входа.

## Модальные окна на телефоне
- **Прокрутка страницы под открытым окном заблокирована** (`frontend/src/useBodyScrollLock.js`, подключён в обеих модалках — `Batches.jsx` и `SettingsModal` в `Purchasing.jsx`). Симптом был: тянешь форму, а вместо неё уезжает список поставок на фоне. Две разные причины, лечатся вместе:
  - *scroll chaining* — прокрутка внутри `.modal-box`, дойдя до края, продолжается на фоне. Лечится `overscroll-behavior: contain` (стоит и на `.modal-box`, и на `.modal-overlay`).
  - *сама страница остаётся прокручиваемой* — лечится блокировкой `body`. Именно `position: fixed`, а не `overflow: hidden`: в iOS Safari (а приложение стоит как PWA) `overflow: hidden` на body не удерживает прокрутку. Побочный эффект `position: fixed` — страница прыгает в начало, поэтому хук запоминает `window.scrollY` перед блокировкой, ставит `top: -scrollY`, а при закрытии возвращает позицию через `scrollTo({ behavior: 'instant' })`.
  - **Важно:** хук блокирует прокрутку на всё время жизни компонента, поэтому модалки обязаны монтироваться условно (`{showModal && <BatchModal/>}`), а не прятаться через CSS — иначе прокрутка останется заблокированной навсегда.


- **Шапка модалки (`.modal-header`) — `position: sticky`, а крестик — минимум 44×44 px.** Из того же расследования: пользователь жаловался, что "крестик не работал". Проверено в браузере на ширине 375 px: форма поставки длинная (14 полей), пользователь прокручивает её вниз к кнопке "Сохранить" — и в этот момент крестик оказывался на **336 px выше видимой области**, то есть его физически не было на экране, закрыть окно было нечем. Плюс сам он был 24×27 px при рекомендованном минимуме 44×44. Если будешь трогать `padding` у `.modal-box` — синхронно поправь отрицательные margin/top у `.modal-header` (значения должны совпадать с padding, есть отдельный набор для `max-width: 640px`, где padding 18 px вместо 24 px).

- **Отступы под вырез iPhone у модалки** (2026-09-01). В `index.html` стоит `viewport-fit=cover`,
  то есть страница рисуется под "чёлкой" и под домашней полосой. Форма поставки длинная и почти
  всегда упирается в максимальную высоту, поэтому её шапка с заголовком и крестиком вставала прямо
  под системные часы. Лечится в `.modal-overlay`: `padding-top: max(20px, env(safe-area-inset-top))`
  и такой же `padding-bottom` с `safe-area-inset-bottom`. Вторая половина лечения — `.modal-box`
  теперь `max-height: 100%`, а не `90vh`: `vh` про вырез не знает, и окно всё равно вылезало бы
  под него, а `100%` считается от высоты `.modal-overlay` уже за вычетом её отступов.
  **Отступы: сверху под вырез, снизу обычные 20 px.** Пробовали и `padding-bottom` под домашнюю
  полосу (34 px — владелец попросил убрать, съедало высоту формы), и `padding-bottom: 0` на
  телефоне (окно упиралось в край экрана и выглядело обрезанным). Остановились на 20 px:
  в отступе видно затемнённую подложку, и вместе с покраской `body` из `useBodyScrollLock`
  он сливается с полосой под окном в одно целое.
  **Полоса под окном на iPhone, которую НЕ убрать из CSS.** По скриншоту владельца: экран 852 pt,
  карточка идёт с 59 pt (это `env(safe-area-inset-top)`) и заканчивается на ~772 pt — то есть
  веб-вью PWA заканчивается примерно на 793 pt, на высоту статус-бара выше низа экрана. Полоса
  ниже — это уже не страница, там просто фон приложения (`theme-color` совпадает с `--bg`,
  поэтому и не отличить). Правкой CSS её не занять: страница туда не рисуется вообще.
  **Чем кончилось (2026-09-01), НЕ переигрывать по кругу.** Переустановка иконки на экран "Домой"
  не помогла. Пробовали убрать `viewport-fit=cover` и поставить статус-бар `black`: полоса внизу
  пропала, окно стало на всю высоту — но статус-бар стал чёрной полосой отдельно от страницы, и
  владелец попросил вернуть цвет меню наверху. **Итоговый выбор — внешний вид:** `viewport-fit=cover`
  и `black-translucent` возвращены, статус-бар красит собой `.mobile-topbar` (её фон `--bg-card`
  и `padding-top: calc(12px + env(safe-area-inset-top))`), а короткое окно осталось как плата.
  Полосу внизу маскируем в два приёма: `background_color` в манифесте приведён к `--bg` (был
  `#0b0f1a`, отличался от фона страницы), а `useBodyScrollLock` на время открытой модалки красит
  `body` в `#090d16` — это `--bg` уже под подложкой `.modal-overlay`, поэтому полоса под окном
  сливается с притемнённым фоном и стыка не видно. Менять `--bg` или прозрачность подложки —
  пересчитывать `MODAL_BACKDROP_BG`.
  **Следствие для CSS:** `env(safe-area-inset-*)` снова живые. Значения написаны как
  `max(20px, env(...))` и `calc(12px + env(...))`, так что работают в обоих режимах.
- **Цвет полосы статус-бара задаёт `theme-color`, и в Safari, и в установленном PWA.** Это
  выяснилось последним (2026-09-01) и противоречит модели, из которой я исходила раньше ("в
  установленном приложении полосу закрывает собой `.mobile-topbar`"): полоса оставалась темнее
  меню, пока в `index.html` стоял `theme-color: #0e1420` (фон страницы), и покрасилась в обоих
  местах сразу, как только его сменили на `#161d2e` (`--bg-card`, цвет верхней панели).
  Владелец подтвердил на устройстве. Так что при смене палитры менять `theme-color` вместе с
  `--bg-card`, иначе полоса разъедется с меню. `background_color` в манифесте — другое: это
  заставка при запуске и заливка вне окна, она равна `--bg`.
  **Открытый вопрос:** раз цвет полосы держится на `theme-color`, возможно, `black-translucent`
  и `viewport-fit=cover` больше не нужны — с `black` окно было на всю высоту (нет полосы внизу),
  а полоса сверху всё равно взяла бы цвет из `theme-color`. Не проверено: владельцу предложено,
  он остался на текущем варианте. Если решите проверить — менять оба мета-тега разом и помнить,
  что iOS перечитывает статус-бар не всегда, может понадобиться переустановка иконки.
  Проверено в браузере с подставленным `59px` вместо `env()`: верх окна встаёт ровно на 59 px,
  снизу 20 px, прилипающая шапка держится у края окна, а кнопка "Создать поставку" при прокрутке
  до конца заканчивается на 773 px при полосе с 778 px — то есть под неё не уходит.
  На десктопе `env()` равен нулю, окно по-прежнему центрируется с отступом 20 px.

- **`input[type="date"]` на iOS шире, чем ему задано** (2026-09-01). Safari рисует такое поле
  нативно и подгоняет ширину под свой текст ("3 сент. 2026 г."), игнорируя `width: 100%`. На
  "Поставках" из-за этого поле дат вылезало шире соседних, и вся страница прокручивалась вбок
  (`.main-content` с `overflow-x: auto` это позволяет). В Chrome НЕ воспроизводится — все поля
  ровно 351 px на 375-пиксельном экране, так что проверять только в браузере тут бесполезно.
  Лечится `appearance: none` на самом поле (у `.toolbar-date`), плюс `input[type="date"]` глобально
  получил `max-width: 100%` на случай других страниц. Календарь по нажатию при этом работает.

## Известные ограничения / что не доделано
- **«География заказов»: три села так и не разобраны** — Карабулак, Ленинский, Аухатты (по одному
  заказу, ~1% выручки). Карабулак встречается в geonames в 17 областях, Ленинский в трёх,
  Аухатты нет вовсе — гадать не стали, они висят в блоке «Не удалось определить область» внизу
  страницы. Как владелец скажет, куда они возились, — дописать в `backend/kzRegions.js`.
- **В сохранённом расчёте юнит-экономики по LUMIX HD остались тестовые значения Claude** —
  пошлина 7% и брокер 180 000 ₸ (см. предупреждение про стенд выше). В сером режиме ввоза они
  на цифры не влияют, но при переключении на белый расчёт соврёт. Владельцу сказано, решение
  за ней; если попросит — обнулить эти два поля.
- **«Бонусы от продавца» в юнит-экономике не подтягиваются автоматически**, хотя данные лежат
  в той же структуре, что и реклама (`bonus_expenses` + `bonus_campaign_products`). Владельцу
  предложено, ответа пока нет.
- Токен Wonder (сессионный) живёт ~10 часов — поэтому сделан логин по email/паролю на каждый вызов, а не хранение статичного токена.
- Причина расхождения 179/214 по Wonder не выяснена — возможно, стоит уточнить у самого Wonder или у владельца магазина, весь ли объём возвратов должен идти через этого партнёра.
- Себестоимость возвратов (`STOCK_CUTOFF_DATE` в `constants.js`) — партии считаются снимком на эту дату, заказы старше неё оцениваются по цене первой поставки.
- На "Закупе" сознательно не сделано: карточка "План закупа" (была пустая 0/0 на скриншоте-примере, непонятна без ручного выбора товаров) и предзаполнение формы поставки количеством из "К закупу" — кнопка "Создать поставку" просто открывает "Поставки" пустой формой (так решил пользователь).
